# NEXUS v0.2 — plano

## Contexto

A v0.1.0 saiu (tag no GitHub, rascunho de release, site no GitHub Pages). Hoje a NEXUS:
- roda só no Windows;
- conecta só o Claude Code (tela Integrações);
- entende TS/JS, Python e Rust;
- não se atualiza sozinha (`docs/release.md` → "Atualização segura (pendente)").

O bot do Discord terminou a etapa 1.

Para a v0.2, o usuário escolheu:
- atualização automática, perguntando na 1ª abertura (sem resposta, não verifica);
- mais agentes, só mostrando a configuração para copiar (o app continua sem escrever fora da pasta de dados dele);
- Go, Java e C#;
- bot do Discord etapa 2;
- Windows, Linux e macOS;
- sem assinatura de código por enquanto.

Princípio que segue valendo:
- cada etapa termina com testes verdes, no CI e localmente, e é mesclada no `main`;
- a `v0.2.0` sai só no fim;
- commits como `eduardodev`.

## Etapa 1 — Base multiplataforma (Windows + Linux + macOS)

É feita primeiro porque a atualização automática precisa dos artefatos de todos os sistemas.

1. **Pastas proibidas no Unix**: `forbidden_reason` em `crates/nexus-core/src/projects.rs` hoje só olha variáveis do Windows.
   - Adicionar a lista Unix, comparada pelo caminho real (usando o `real()` que já existe):
     - Unix em geral: `/`, `/usr`, `/etc`, `/bin`, `/sbin`, `/var`, `/opt`, `/proc`, `/sys`;
     - só macOS: `/System`, `/Library`, `/Applications`.
   - A pasta pessoal já é tratada.
   - Testes com `cfg(unix)`.
2. **Links no Unix**: `scan.rs` checa reparse points no Windows (`#[cfg(windows)]`). Garantir o equivalente com `symlink_metadata`.
   - O teste `links_outside_the_project_are_not_followed` ganha versão com symlink Unix.
3. **CI** (`.github/workflows/ci.yml`): incluir `macos-latest` na matriz Rust, que já tem windows e ubuntu.
   - Frontend e E2E (WebView2) continuam só no Windows.
4. **Release em matriz** (`.github/workflows/release.yml`):
   - `windows-latest` → NSIS;
   - `ubuntu-22.04` → `.deb` + `.AppImage`;
   - `macos-latest` → `.dmg` aarch64 e x86_64, com `--target`.
   - Cada job compila a CLI como sidecar e roda `cargo test` antes.
   - Um job final junta tudo num único rascunho de release, com `SHA256SUMS.txt`.
5. **Script de release multiplataforma**: `scripts/release.ps1` passa a rodar em `pwsh` 7, que existe nos três runners. Ajustes:
   - sufixo `.exe` só no Windows;
   - triple do alvo;
   - pastas de bundle por sistema.
6. **`tauri.conf.json`**:
   - `bundle.targets` por sistema, via `tauri.release.conf.json`;
   - bloco `linux.deb` (dependências do webkit2gtk);
   - `macOS.signingIdentity: "-"` (assinatura ad-hoc, necessária no Apple Silicon);
   - `minimumSystemVersion`.
7. **Fumaça dos artefatos no CI** (não há Mac nem Linux com interface para testar à mão):
   - instalar ou extrair o pacote;
   - rodar `nexus --version`;
   - rodar `nexus mcp serve` com um `initialize` + `tools/list` via stdin.
8. **Docs**:
   - `docs/release.md`: como abrir no macOS sem assinatura (`xattr -dr com.apple.quarantine`) e no Linux;
   - `docs/roadmap.md`: fase "v0.2".

Risco declarado: a interface no Linux e no macOS só é validada por build + fumaça da CLI/MCP. Teste manual da janela fica para quem tiver o sistema; isso vai registrado no roadmap.

## Etapa 2 — Atualização automática (opt-in)

1. **Plugins** `tauri-plugin-updater` + `tauri-plugin-process`, na versão 2.x fixada como os demais em `Cargo.toml` do workspace. As capabilities dão permissão só ao necessário.
2. **Chaves**:
   - **o usuário** gera o par com `pnpm tauri signer generate`;
   - **o usuário** grava a chave privada e a senha como segredos do GitHub (`TAURI_SIGNING_PRIVATE_KEY`, `..._PASSWORD`) com `gh secret set`. Eu não manipulo a chave privada;
   - a chave pública vai para `plugins.updater.pubkey` no `tauri.conf.json`.
3. **Endpoint**: `https://github.com/EduardoxDev/Nexus/releases/latest/download/latest.json`.
   - O job final do release gera `latest.json` com:
     - `windows-x86_64` (NSIS);
     - `linux-x86_64` (AppImage; o `.deb` não se atualiza sozinho);
     - `darwin-aarch64` e `darwin-x86_64` (`.app.tar.gz`).
   - Cada entrada leva sua `.sig`.
   - `bundle.createUpdaterArtifacts: true`.
4. **Preferência** em `crates/nexus-core/src/settings.rs`:
   - novo campo `update_check: UpdateCheck { Ask, On, Off }`, com padrão `Ask`;
   - migração de settings compatível (o campo novo assume o padrão);
   - contrato TS regenerado (ts-rs).
5. **Desktop**:
   - na 1ª abertura com `Ask`, um aviso na Visão geral: "Verificar atualizações no GitHub? Isso envia seu IP e a versão do app." Botões Permitir / Agora não;
   - com `On`, verifica ao abrir, no máximo 1×/dia;
   - "Versão X disponível" → mostra as notas → "Instalar e reiniciar";
   - Configurações ganha o seletor e o botão "Verificar agora", que funciona mesmo com `Off`.
   - A chamada é feita no Rust pelo plugin. A CSP do webview continua fechada.
6. **Privacidade**: atualizar `docs/privacy.md` (única conexão de rede, opcional) e o FAQ do site (`apps/web/src/sections/Faq.tsx`).
7. **Testes**:
   - unidade da regra 1×/dia e dos estados `Ask`/`On`/`Off`;
   - E2E: com `Ask`, o aviso aparece e "Agora não" não faz requisição.
   - Teste real: publicar uma `v0.2.0-rc.1` e depois uma `rc.2` e ver a `rc.1` se atualizar no Windows. Linux e macOS são testados pelo CI até onde dá.

## Etapa 4 — Go, Java e C#

Mesmo padrão léxico dos analisadores atuais (`crates/nexus-core/src/analysis/{typescript,python,rust_lang}.rs` + `lexer.rs`). O `classify.rs` já detecta `go`/`java`/`csharp`.

1. **Analisadores**: `go.rs`, `java.rs` e `csharp.rs`, registrados em `analyzer_for` (`analysis/mod.rs`) e na lista de cobertura declarada, que a interface mostra.
   - Remover o teste que hoje espera `analyze(Some("go"), …)` ser `None`.
   - **Go**: `func` (inclui métodos com receiver), `type … struct/interface`, `const`/`var` de topo; `import` simples e em bloco.
   - **Java**: `package`, `class`/`interface`/`enum`/`record`, métodos e campos públicos; `import` (inclui `static` e `.*`).
   - **C#**: `namespace` (bloco e file-scoped), `class`/`interface`/`struct`/`record`/`enum`, métodos e propriedades; `using`.
2. **Resolução** (`analysis/resolve.rs`):
   - **Go**: ler o `module` do `go.mod`; um import do módulo aponta para os arquivos `.go` da pasta (sem `_test.go`).
   - **Java**: `a.b.C` → arquivo cujo `package a.b` declara `C` (busca por sufixo `a/b/C.java` + checagem do package).
   - **C#**: `using X.Y` → arquivos que declaram `namespace X.Y` (via um índice de namespaces montado na passada).
   - Ida para pacote (Go/C#): novo `Target::Files(Vec<String>)` com limite (`MAX_ITEMS`). O `graph.rs` cria uma edge por arquivo.
3. **Fixtures**: `tests/fixtures/{go-service,java-app,csharp-lib}`, com gabarito conferido à mão como o atual (`docs/evaluation.md`). Meta: 100% em declarações e imports nas fixtures.
4. **Desempenho**: rodar `scripts/bench.ps1` e registrar em `docs/benchmarks.md`.
5. **Docs**: ADR curto (extensão do ADR-0012), atualização do `docs/architecture.md` e do site (o card "Entende o código" passa a listar as 6 linguagens).

## Etapa 5 — Bot do Discord, etapa 2 (`apps/discord-bot`)

1. **Estado do bot** em SQLite com `node:sqlite` (embutido no Node 24, sem dependência nova), em `NEXUS_DATA_DIR/../bot.db`, num módulo `src/state.ts` com testes.
2. **Anúncio de versão**:
   - a cada 15 min, `GET https://api.github.com/repos/EduardoxDev/Nexus/releases/latest`, sem token, dentro do limite de 60/h;
   - tag nova → embed com nome, notas resumidas e links de download por sistema no canal `announceChannelId`;
   - guarda a última tag anunciada (não repete ao reiniciar).
   - Rascunhos não aparecem nessa API, então só anuncia o que você publicou.
3. **Avisos internos**:
   - a cada 15 min, chama no MCP `get_stale_context` e `get_index_status` para os projetos da equipe;
   - alertas novos (por id estável) vão para `teamAlertsChannelId`;
   - falha de índice também é avisada, com dedupe.
4. **Config**: `bot.config.json` ganha `announceChannelId`, `teamAlertsChannelId` e `githubRepo`, validados como os campos atuais em `src/config.ts`.
5. **Comando** `/nexus versao`: versão instalada da NEXUS + a última release.
6. **Correções pendentes da etapa 1**:
   - M2: regra de caixa;
   - M5: latência;
   - M6: caminhos longos;
   - M7: corte do resumo do pack.
7. **Testes**: vitest com `fetch` falso para o GitHub e o `nexus mcp serve` real sobre a fixture `saas-app` para os alertas, como na etapa 1.
